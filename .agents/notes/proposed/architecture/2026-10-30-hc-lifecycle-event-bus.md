# Agent Note: HC 模块的受托管生命周期与事件接入

Status: proposed

## Problem

用户明确希望以 MC 事件系统与 KJS 监听形式为使用体验参照：HC 有事件总线 HcEvent，Store 消费方只把 `cs.Open` 挂到 Store Init 事件，下载与纳入等操作放进对应事件处理器；事件触发、执行顺序、资源与生命周期归 HC 处理，消费方不逐一管理这些事项。上一份候选只把事件用于仓库打开后的扩展，未覆盖事件驱动模块加载这一意图。

本篇记录已明确的设计方向，尚未实施。下面的宿主类型、方法名称、加载与关闭协议属于助手提出的候选细节，不代表用户已确认完整 API，也不表示必须复刻某个 MC 加载器或脚本引擎的全部语义。

## Proposal

### 已明确的方向

- 注册监听与执行操作分开。注册时保存处理器，Store 模块进入加载阶段时才调用处理器中的打开等操作。
- 事件总线参与 HC 模块的生命周期组织，由所在共享运行时实例持有，不局限于打开完成后的通知。
- Store 消费方使用注册式入口，不承担手动启动、加载、卸载 Store 或组织资源收尾的责任；下载、纳入等操作也允许在对应事件处理器中声明。HC 模块声明事件与 Store 资源职责，共享运行时组织执行和收尾。
- 生命周期描述阶段与状态，不要求实例占用一个线程或常驻线程池。实例、订阅与服务可以在内存中保留，直到宿主显式关闭。
- 用户进一步明确，库提供封装完整、可直接调用的下载、纳入、校验和启动等业务能力；“没有默认业务行为”是指库不自行决定做哪些业务，不是缺少能力实现，也不是要求消费方自己实现或逐个转发算法。
- 消费方在挂载点中调用所需能力，表达业务意图；运行时负责挂载点触发、执行组织和生命周期回收。这是受托管的执行环境，而非把每个业务方法额外包装成一个必须由消费方接线的转发监听器。
- 消费入口可用回调或特性与源生成绑定，具体默认尚未选定；用户还希望回调入口能桥接 JS/TS，脚本运行时和桥接契约尚未设计。

### 生命周期托管与操作入口分别比较

当前模型的分工是：库负责业务能力实现，消费方负责在挂载点中表达业务意图，运行时负责执行保障。此前独立评估和助手把它理解为默认业务库之外再要求消费方逐个转发操作，这个前提已由用户澄清；不能据此继续批评用户要求消费方重写下载或校验，或认为监听器仅是无差异转发包装。

更小的候选是消费方提供 Store 配置，由 HC 执行必要的打开步骤；消费方通过受托管的 Store 操作入口直接提交下载或纳入，入口内部同样检查就绪、登记在途操作、响应取消并参与退出收尾。事件只承载实际需要的生命周期扩展、进度与完成通知；可替换算法或策略用明确的策略契约表达。这里的直接入口不是把现有底层 Store 引用裸露出去，不能绕过运行时跟踪。

受托管直接入口仍可作为另一种消费形式比较，但不把它预设为比挂载点更完整的业务能力实现。后续讨论应验证挂载点是否真实管理异步完成、结果、取消和资源有效期，并区分阶段、单次操作及观察通知的执行契约。挂载点中的 Open 也应从消费方选择何时打开哪个仓库来理解，不能只因它是调用动作就判定为生命周期责任泄漏。特性与生成器用于声明检查和自动接线，不应独占业务能力，也不替代运行时的执行保障。

### 第一轮运行规则讨论

用户要求进一步讨论 HC 事件总线与生命周期。本节为助手提出的讨论基线，不将建议写成已确认契约；此前已明确的消费方注册处理逻辑、HC 托管生命周期保持不变。

通用运行时、类型化事件派发和操作调度的职责上移至共享框架：运行时持有模块状态、资源和依赖图；总线管理监听与派发；调度部分跟踪请求的结果、并发、取消和结束。具体类型和包归属尚未确定，这三项是职责划分，不要求立刻各建一个程序集，也不要求各有常驻线程。

本轮优先讨论三项会改变消费体验的取舍：

1. **启动时机。** 建议由应用集成入口统一启动已选择的模块，启动前完成声明收集与配置验证；不因第一次订阅就隐式启动，不要求 Store 消费方单独启动。另一种是能力首次使用时延迟初始化，能避免未使用能力的初始化成本，但会把配置或打开错误推迟到首个业务请求。
2. **挂载点分类与完成规则。** 库完整提供业务能力、消费方在挂载点调用所需能力的分工已经明确，不再让用户选择是否自行实现标准下载。仍需讨论哪些挂载点属于一次初始化阶段、哪些随一次业务请求触发、哪些只是观察通知；分别明确触发方、输入、可调用能力、等待范围、结果和失败传播，避免一套监听语法掩盖不同完成契约。
3. **重新加载。** 建议第一版运行时按一次启动、一次受控停止组织，停止后用新实例重新开始；启动前确定模块集合与依赖，生命周期监听按对应阶段的窗口接入，运行监听允许动态订阅与释放。另一种是支持运行中替换模块或重新触发生命周期，需要额外明确在途任务、资源借用、旧上下文失效和再次初始化的规则，不能从普通事件订阅自动推导。通用机制归属共享运行时，下文只记录 HC 接入；早期未确认的 HC 内置宿主假设不再作为当前分层。

建议的最小运行时状态是：创建、收集注册、启动、运行、停止、已停止；启动失败显式进入失败状态，并收尾已成功初始化且由本次运行时拥有的资源。模块各自有初始化、就绪、停止及失败状态，依赖模块就绪后才启动下游。最终事件名称、可选模块失败策略和失败后的清理状态仍需细化，不承诺所有失败都能继续运行。

事件上下文按阶段提供能力：Store Init 允许声明或执行 Open；Store 就绪后才接受普通下载或纳入。初始化期间不能通过普通请求入口等待一个依赖本次初始化完成才会运行的工作；需要的初始化操作使用阶段内明确可用的能力，避免初始化等待自身就绪。Open 的配置来源与冲突检查集中处理，多个 Init 监听器不能各自默默打开不同 Store。

生命周期阶段建议可等待并按显式依赖推进；普通操作由调度和原有存储锁控制并发，不把整个 HC 总线锁住直到下载结束。停止先拒绝新请求，再按既定退出策略等待或取消在途工作，保留完成与错误的报告能力，最后按依赖反序收尾资源。不能以统一事件设计为由把所有操作都改成退出时立即取消，也不在全局总线锁内等待处理器。

### NeoForge 与 Minecraft 的生命周期参考

用户指出 NeoForge 是更现代的社区加载器典范；本轮以 NeoForge 为主要参考，Forge 只保留沿革对照。以下记录参考实现的事实和对 HC 候选的限制，不表示 HC 已采纳其全部规则，也不复制第三方代码。查阅日期为 2026-10-30；NeoForge 固定在 `26.1.x` 分支提交 `67b94a8c09e550ec61708ce0e3d951e60fe3ac9a`，该提交对应 Minecraft `26.1.2`、Bus `8.0.5`。文档使用其 26.1 版本，不把默认开发分支当成相同版本。

- **两条总线各有职责。** 每个 Mod 的 Mod Event Bus 承载该 Mod 的加载与部分注册事件；`NeoForge.EVENT_BUS` 是游戏事件总线，拒绝 `IModBusEvent`。官方文档要求在 Mod 构造器或自动订阅入口注册处理器，再由加载器触发 Construct、注册、Common Setup、侧特定 Setup、IMC 和 Load Complete 等阶段。多数加载阶段在 Mod 之间并行派发，需要主线程的工作由 `enqueueWork` 排入阶段工作队列；不能因此推断任意异步业务都自动受到总线跟踪。
- **游戏总线有启用时机，但没有冻结全部监听表。** `CommonModLoader.begin` 先收集并构造 Mod，完成 registry 初始化、注册数据冻结和配置加载，再调用游戏总线的 `start`；Common Setup、侧特定 Setup、IMC 和 Load Complete 在其后的 `load` 中执行。这里冻结的是 registry 数据，不是监听绑定。不能把“构造时注册、然后推进阶段”的惯例解释成总线在启用前验证并永久固定所有监听器。
- **Bus 自身的状态很小。** Bus 8.0.5 的 `register`、添加监听和 `unregister` 不以启用状态作为注册开关；`start` 只解除停用标记。停用时的 `post` 直接返回事件，不派发、不排队，也不在启用后补发。正常 `post` 同步调用取得的监听数组，处理器异常经异常回调后继续抛出；运行中移除监听不表示正在执行的派发会立即中止。该版接口只有 `start`，没有旧 Forge 的 `shutdown`，也没有等待在途工作、资源释放或不可逆关闭协议。不能把它描述成完整的“注册中、运行中、收尾中、已关闭”状态机。
- **总线存续与游戏对象的生命周期分别组织。** Minecraft 原有的客户端、服务器循环及资源加载负责实际推进；NeoForge 在这些位置加入钩子，经同一游戏总线派发服务器 About To Start、Starting、Started、Stopping、Stopped。服务器停止路径释放该服务器相关状态，没有关闭全局游戏总线；客户端离开单人世界与退出客户端进程是不同路径。现代客户端还分别提供 Started、Stopping、Stopped，最后一项在客户端资源已释放、进程即将结束时派发，总线仍承担收尾通知。
- **资源重载有自己的收集和执行窗口。** 每次服务端资源重载通过 `AddServerReloadListenersEvent` 收集本次重载的监听器；`SortedReloadListenerEvent` 检查具名键与监听实例重复，并允许声明依赖。事件返回后进行拓扑排序和循环依赖检查，再交给 Minecraft 的 `SimpleReloadInstance` 执行；重载上下文在成功完成后清除。这是单次重载工作表的收集、验证与执行，不是重建整个事件总线或重新加载全部 Mod。

对 HC 的直接启示仍是候选：总线是否能够派发、加载阶段推进到哪里、某项资源是否就绪及是否正在收尾，应分别表达。此前“首次派发前固定所有执行绑定”的建议是 HC 可以另选的约束，不能声称 NeoForge 已采用同样规则。是否允许动态执行绑定、哪些阶段具有独立注册窗口、如何等待在途工作和最终关闭，仍需根据 HC 的受托管执行需求讨论。

### 共享运行时中的 HC 接入

用户明确生命周期、总线、任务等待与资源回收等通用机制应上移至独立共享运行时，为 HC 与 Gebinde 提供共同的执行环境。本篇只负责 HC 如何接入；之前的通用四态、阶段窗口与派发草稿迁出，不再把 HC 专属宿主作为框架归属。分层方向已明确，具体包名、接口和迁移尚未实施。

- HC 提供 Store、下载、纳入、校验和启动等完整业务能力，并声明自身阶段、能力依赖和资源归属；共享运行时组织调用、等待、取消和回收。
- hcEvent.Store.Init 等仍可作为 HC 的消费外观，Open 在对应阶段调用现有业务能力。外观接入所在共享运行时的通道，不另建一套通用事件内核。
- 模块就绪条件和实际资源释放由 HC 模块声明和实现；共享框架不内置 Store 或 Minecraft 业务。资源所有权不因上移而转给消费者或借用转接。
- 建议以可选模块接入层连接运行时，使现有 Store 工厂与直接消费继续可用；独立使用 Store 不强制启动完整宿主或引入 Gebinde。
- 总线的状态、动态订阅、阶段窗口、派发与最终收束由共享运行时契约统一定义；本篇不再独立决定一组 HC 专用通用接口。此前 Hc 前缀的相关类型均为临时草稿名称，不是现有公共 API。

### 候选调用形状

以下代码只展示消费方注册，类型和成员尚不存在；`hcEvent` 是 HC 提供的当前实例事件入口：

```csharp
hcEvent.Store.Init(cs =>
{
    cs.Open(storePath, http, downloadOptions);
});

hcEvent.Store.Ready(cs =>
{
    // The store is available to consumers in this phase.
});
```

这里的 `cs` 是 Store 初始化或就绪事件的上下文，不是增加了实例 `Open` 方法的现有 `IContentStore`。候选 `cs.Open` 委托现有创建器，由 HC 保存本次实例并处理后续生命周期。具体事件名称、上下文类型与操作结果表达仍需设计。

HC 运行时与应用启动、受控关闭的衔接集中在一次性的宿主集成层，Store 消费方无需调用 `LoadAsync` 或 `UnloadAsync`。HC 据该衔接触发初始化、组织加载并收尾。宿主集成不能依靠注册监听器自行推断应用何时准备好或何时需要停止；具体自动接入形式尚未确定，不承诺仅引用程序集即自动完成。

### 助手对操作事件的意见

以下是本轮讨论的建议，尚未作为用户已确认的细节：

- 支持消费方在事件处理器里声明下载与纳入，由 HC 统一等待、调度、取消和报告结果；不要求消费方自行持有 Store 的启动与停止状态。
- 初始化、就绪、停止等属于生命周期阶段；下载和纳入是可以重复发生的业务请求，不宜为每个请求增加一次 Store 生命周期转换。业务方仍须提供请求的发生时机和输入，HC 不能仅凭订阅推断何时下载什么。
- 请求事件按一次请求一次完成来处理，明确唯一执行责任；进度、完成与失败通知允许多个观察者订阅，避免新增日志监听器时意外重复下载。监听语法可以统一，但调度契约应区分请求与通知。
- 操作处理器返回可等待的 Task 或 ValueTask，HC 收集成功结果或显式传播失败，并规定取消与执行顺序。不要用不能等待的 async void 承载受托管操作，也不要要求消费方从后续广播中自行拼出请求结果。
- 事件上下文承载当前阶段或请求所需的能力，不能在就绪前或关闭后继续绕过 HC 执行；初始化顺序与依赖检查由 HC 负责，不能依赖消费方碰巧先注册某个处理器。

### 监听声明方式的比较

用户提出比较 KJS 式回调注册与 Forge 式特性监听，并考虑由源生成器产生 AOT 兼容的注册代码。本节记录备选方案与助手倾向，用户尚未选定具体声明方式；前文回调代码只是候选示例。两种写法都交给同一个 HC 生命周期与调度实现，不各自维护一套事件语义。

- **回调注册**：直接声明类型化委托，适合少量处理器、局部闭包、动态订阅和测试。优点是跳转、执行关系直接，不引入编译期工具；模块增多后仍需维护集中注册入口，也要检查是否漏注册。回调并不要求运行时生成代码，AOT 不是放弃这种声明形式的理由。
- **特性与增量源生成器**：监听方法通过 C# Attribute 标记，使用 Roslyn `IIncrementalGenerator` 与 `ForAttributeWithMetadataName` 收集声明，生成直接方法或委托绑定，以及项目级注册表。适合监听点分布于多个 HC 模块的主要入口；可配套 analyzer 检查签名、不可等待的异步 void、不可访问的方法和可静态判断的重复声明。收益是减少逐项注册，并把部分声明错误提前到编译期；代价是生成器、诊断、包分发和 IDE 行为都需要维护。

助手更倾向以特性加生成器作为模块监听的主要入口，保留回调作为底层注册与显式订阅能力。它对应用户希望消费方只声明处理器的体验；不把该倾向写成用户已确认的决定。HC 执行过程仍管理实例、依赖、阶段、操作与退出，生成器只生成绑定，不在编译时打开仓库或执行消费方处理器。

生成注册表按当前 HC 实例接入，监听器可由组装入口提供依赖，不要求全部使用静态方法或全局单例。每个含监听器的消费方项目需要参与生成，不能只在 HC 自身编译时扫描未来才出现的消费代码。跨程序集的注册清单与 HC 集成入口怎样连接仍需明确；生成文件存在不代表它会自动被执行。不以 JIT 下反射扫描作为默认补漏路径，避免生成遗漏在开发时被掩盖。

### 回调、特性与脚本接入

用户希望回调入口能桥接 JS/TS；以下是助手对实现的建议，尚未选定引擎、包或公开契约：

- 回调、特性生成绑定和脚本桥接接入同一套挂载点、执行上下文与业务能力，具备一致的结果和生命周期保障；不让特性处理器专享某些必要能力，也不为脚本维护另一套阶段规则。
- JS/TS 接入需要明确脚本运行时、数据和资源句柄转换、异步结果与取消传递、上下文何时失效，以及脚本错误怎样关联到宿主操作。可注册回调只提供接入位置，不自动解决跨运行时协议。
- 挂载点结束前必须能判断它负责的工作是否完成；由上下文创建或接管的资源需要明确归属和回收。不能因为入口来自脚本就允许任务失去跟踪或在上下文关闭后继续访问已释放的能力。
- 脚本桥接属于另外的语言接入设计，不从这项意图推导修改现有 C ABI 或允许 C# 直接回调 Dart；既有跨语言边界仍按原约束处理。

### 编译期工具与 JIT 的界限

- 生成器在 IDE 或编译器宿主中执行，不随 HC 运行时产物一起执行；生成的 C# 代码再参与正常编译和 NativeAOT 发布。把声明分析和绑定移到编译期，可以让消费方少写受 AOT 约束的注册代码。
- 生成器分析尚未编译的消费方代码时使用 Roslyn 语法与符号模型，不等于先反射加载并执行消费方程序集。不要把任意业务启动逻辑提前在构建时运行。
- 常规源生成器添加代码，不改写任意已有方法体。为私有监听方法生成同类桥接需要可扩展的声明形状，例如 partial 类型；具体可见性规则必须诊断清楚。
- 特性并不自动把监听器正文中的运行时 Reflection.Emit、动态加载未知托管程序集或其他 JIT 专属能力转换为 AOT 代码。若消费方业务本身需要这些能力，需要单独设计可生成的声明或 AOT 实现；也可为明确选择 JIT 的宿主提供独立可选能力，但不由事件注解隐式保证兼容。

资料依据：[Roslyn 增量生成器](https://github.com/dotnet/roslyn/blob/main/docs/features/incremental-generators.md)、[增量生成器 cookbook](https://github.com/dotnet/roslyn/blob/main/docs/features/incremental-generators.cookbook.md)、[NativeAOT 限制](https://learn.microsoft.com/en-us/dotnet/core/deploying/native-aot/)、[Forge 事件监听形式](https://docs.minecraftforge.net/en/1.21.x/concepts/events/)。Forge 只作为声明体验参考，不承诺复制其自动静态订阅方式。

### 候选边界与待定契约

- 总线按共享运行时宿主实例持有，维持现有不使用全局静态可变注册表的约束。调用外观可以像事件分组，多个宿主的订阅不能互相影响。宿主是可选的组装入口，现有工厂与直接 API 继续可用，不要求消费方采用特定 DI 容器。
- HC 宿主和模块的最小阶段候选为注册、加载、就绪、停止、已停止，加载失败显式返回失败；它们与共享运行时定义的总线状态分别表达。Store 未成功打开时不发布就绪事件；同一宿主的重复加载、重复打开和关闭后重载的行为在接口实现前明确。
- 模块加载依赖由宿主定义，不能通过监听器碰巧的注册顺序表达。派发顺序与异步等待由共享运行时统一定义；模块依赖、独立模块并行与具体阶段完成条件继续由运行时定义。异步监听使用可等待的 Task 或 ValueTask 回调，并由阶段入口等待，不能把异步代码传给 Action。
- 事件总线本身不必有后台循环；发布时直接调度并等待处理器即可。事件派发与任务调度分别负责时机与线程。当前 `ContentStoreFactory.Open` 含同步磁盘访问，候选 `LoadAsync` 的名称不能当作它自动离开 UI 线程的保证。
- 共享运行时在收到应用的受控停止信号后驱动 HC 模块关闭，并明确何时拒绝新工作、如何等待或取消进行中的操作、何时发送关闭通知和释放 HC 拥有的资源；Store 消费方不逐一编排。当前 Store 没有 Close 接口；不能把 GC 或回调返回当作关闭。现有直接工厂借用的 HttpClient 所有权不变；新事件入口若也接收借用的 HttpClient，其最终释放仍归提供方，不能暗中改变所有权。
- 加载处理器失败、部分加载后的资源清理、取消和关闭失败须有明确结果，不能吞掉异常再发布成功。加载回调完成后需要持续监听的任务必须登记所有权和结束条件，不能启动无人等待的异步工作。

## Alternatives considered

- **HC 托管生命周期，直接业务入口加扩展通知。** 好处是消费方可直接表达标准操作，HC 仍统一处理就绪、调度和收尾；事件保留给扩展和通知。代价是不能仅凭统一挂载点描述消费方的业务编排，跨语言入口和执行上下文仍需设计。它是未选定的其他消费形式，不代表只有这个方案才有完整业务实现，也不以用户需要自行实现或转发下载为比较前提。
- **仅使用工厂创建并通过构造函数注入。** 好处是调用直接、依赖清晰，当前实现已支持；仍保留为直接入口，但单独采用无法表达用户要求的注册监听后分阶段加载。
- **仅在仓库打开成功后通知扩展。** 好处是监听器拿到的 Store 已可用，生命周期契约较少；此前候选采用这一边界，但没有覆盖通过加载事件安排 Open 操作的需求，因此改为区分加载阶段与就绪通知。
- **仅提供回调声明。** 好处是实现直接且无需生成工具；目前仍是有效方案，但对于分散在多个模块中的监听方法，助手更倾向由特性与生成器减少注册维护。具体选择尚未由用户确认。
- **特性声明，JIT 反射扫描与 AOT 生成器分别发现处理器。** 好处是可以先用反射原型开发；助手不建议作为默认架构，因为漏装生成器、跨项目清单遗漏等问题可能仅在 AOT 发布后出现。同一份生成绑定也用于普通 JIT 构建，更容易核对语义一致性。

## Acceptance criteria

- 注册 Store 监听器不打开仓库；由 HC 进入 Store 初始化阶段才执行监听器内的 Open，成功后才发送就绪通知；Store 消费方不需手动调用加载和卸载。
- 若采用操作事件建议，验证请求结果、失败、取消与通知关联；增加观察者不增加下载或纳入的执行次数。
- 若选择特性入口，验证签名和可见性诊断、项目级清单接入、同实例重复注册、跨项目监听器、普通 JIT 构建与实际 NativeAOT 发布的一致行为；不能只测试生成字符串。
- 回调和特性入口对同一挂载点提供一致的能力、等待、结果、取消和收尾语义；若接入 JS/TS，进一步验证异步映射、错误传播和过期上下文，不能只验证脚本回调被调用。
- 验证两个宿主订阅隔离、阶段与模块顺序、异步处理器等待、重复加载与关闭后调用的明确结果。
- 验证加载失败、部分成功后的清理、取消、停止新工作与在途操作的收尾，不发布虚假的成功状态。
- 直接工厂契约与已有 Store 测试继续成立；HttpClient 所有权不改变，不新增持续轮询线程作为事件派发的必要条件。
- 实施前明确上述待定的公开契约；笔记通过 `npm run verify-notes`。

## Risks

- 动态订阅和快照规则意味着取消绑定不撤回已接纳的调用；监听器资源的释放必须协调在途派发。处理器不结束时，关闭不能保证及时完成；不能用提前标记已释放或强行回收仍被使用的资源掩盖这一事实。
- 事件驱动会把操作的实际执行时间推迟到阶段触发，调试与错误定位需要显示所属宿主、模块和阶段。
- 初始化顺序、失败收尾与关闭语义增加公开契约成本；仅复制监听语法而没有宿主状态机，会留下订阅从未触发或资源无人收尾的问题。
- 使用 MC 与 KJS 作为体验参照不代表兼容其加载器、脚本执行环境、热重载或线程语义；这些不从事件总线的命名自动推导。
- 源生成器会增加构建与 IDE 维护成本；未参与编译的动态监听器不能仅靠静态清单自动支持，生成绑定也不能修复任意监听器正文中的 JIT 专属调用。
