# Agent Note: Store 创建入口的回调配置与生命周期事件

Status: proposed

## Problem

用户希望公开库的调用方式便于人类阅读，并提出为 `ContentStoreFactory` 增加回调与链式 DSL，以及用 `ContentStoreEvents.Open(e => { ... })` 表达生命周期操作。现有工厂只有打开目录和组装已有仓库两种入口，参数数量有限；配置语法的价值主要在于呈现配置意图和组织可选设置，生命周期事件则增加了触发时机与宿主所有权的契约，需要分别评估。

本篇记录供讨论的候选方案，尚未确定采用，不包含实现改动。既有消费方契约和默认创建方式继续有效。

## Proposal

### 配置回调候选

建议保留现有 `Open`、`Create` 签名，考虑增加同步配置回调重载：根目录或已有 `ContentStore`、借用的 `HttpClient` 作为显式必填参数；回调通过一个轻量配置类型提供链式方法。配置结束后由工厂创建并返回 `IContentStore`，回调内无需调用 `Build`。

以下仅为候选调用形状，方法名尚未实现：

```csharp
IContentStore store = ContentStoreFactory.Open(root, http, b => b
    .WithDownloads(new DownloadOptions
    {
        UserAgent = "my-launcher/1.0",
        MaxConcurrentRequests = 8
    })
    .WithOpenMode(StoreOpenMode.CreateIfMissing));
```

- 链式方法只记录配置；配置回调同步执行一次，配置完整性检查须在打开仓库前完成。不得接受会变成 `async void` 的异步配置流程。
- 复用当前不可变的 `DownloadOptions`，不为每个现有下载属性再复制一套 fluent 方法或嵌套 builder。
- 已有 `ContentStore` 的创建入口可以采用同样的下载配置形状，但不提供打开模式，避免对已经打开的仓库表达无效配置。
- 返回的 `IContentStore` 继续由调用方注入并复用；回调结束不代表仓库被释放或任务被取消。`HttpClient` 的所有权仍归调用方，不引入自动释放、隐式缓存或全局单例。
- 底层存储、下载、重试、锁、校验和取消算法继续使用现有实现。

### 生命周期事件候选

本节保留最初的打开后扩展候选。用户已明确希望以事件总线组织模块加载，使 `cs.Open` 等操作延迟到 Store 加载阶段；当前生命周期方向由 [HC 宿主生命周期与事件总线](2026-10-30-hc-lifecycle-event-bus.md)接手。本篇的配置回调候选仍独立保留；本节及备选方案中的“仅用于生命周期扩展”不再是对需求的限制。

`ContentStoreEvents.Open(e => { ... })` 可以表达注册一个在仓库打开时执行的处理器。它的含义须与立即创建实例的配置回调区分：注册阶段记录处理器，由工厂或宿主在真正打开仓库时触发；`Opened` 的命名更明确地表达打开成功后，也可以保留用户偏好的 `Open` 并写清时机。此候选尚未实现，也未替代现有创建契约。

建议采用以下范围：

- 事件入口属于具体宿主或显式传入的事件集合实例，避免全进程共享的静态可变订阅表；调用外观可以接近 KJS，而所有权仍按实例隔离。
- 打开成功事件提供已经可用的 `IContentStore`，适合初始化扩展与记录状态。工厂继续返回同一个接口实例，消费方继续通过构造函数注入。每次成功创建返回实例的触发次数须明确，不把磁盘仓库身份等同于进程内实例生命周期。
- 只包装配置并立即创建的回调仍属于配置回调，不以事件名暗示未来触发或广播。
- 现有 `ContentStore` 没有 `Close` 或释放接口。关闭事件需要宿主定义停止接收任务、取消或等待进行中操作的过程；不能从回调结束、引用消失或 GC 推导关闭。
- 如允许处理器执行异步仓库操作，应采用可等待的任务回调与相应的异步触发入口，不把它传给 `Action` 形成 `async void`。实现前还需确定处理器顺序、异常传播与打开后处理器失败时的实例交付方式；此候选不添加这些运行时机制。

## Alternatives considered

- **保持现有工厂，调用方使用命名参数与对象初始化器。** 好处是公开类型最少，必填依赖直接显示在签名中；当前配置量下已经足够清楚。它仍是有效的低成本选择。候选 DSL 的额外收益在于集中呈现可选设置和提供链式补全，而非新增存储能力。
- **将所有参数和所有下载选项都包装成链式方法。** 好处是风格统一、整段调用可连续书写。代价是新增更多公开方法，并把遗漏根目录、HTTP 客户端等错误推迟到创建时；当前建议保留必填参数并复用 `DownloadOptions`。
- **以生命周期事件统一所有 Store 消费。** 好处是入口贴近 KJS，扩展可以集中声明在何时工作。代价是普通消费也依赖注册顺序与触发方，依赖关系更难从构造函数看出。当前建议把事件用于生命周期扩展，常规操作继续通过注入的 `IContentStore` 调用。

## Acceptance criteria

- 如采纳，文档同时展示直接工厂调用和回调重载，示例返回可用于构造函数注入的 `IContentStore`。
- 既有公开签名和所有权约束保持兼容；新入口与直接入口的行为一致。
- 验证缺失下载配置、回调异常、默认打开模式、已有仓库身份和 HTTP 所有权；配置失败不得先创建仓库。
- 现有测试继续通过，笔记校验通过。
- 如采纳生命周期事件，验证宿主间订阅隔离、准确触发时机与次数、打开失败和处理器异常；如支持异步处理器，验证等待与取消语义。

## Risks

- 当前参数数量较少，新增配置类型和方法的维护成本可能高于阅读收益；保留直接入口使调用方可自行选择。
- 配置回调可能遗漏必填下载设置，需要明确的创建前验证。
- 配置回调候选的方法命名若暗示生命周期作用域或自动资源管理，会误导调用方；文档必须说明这类回调只用于配置。
- 生命周期事件候选还需要明确谁打开和关闭实例、谁持有订阅，以及处理器失败怎样传播；它比单纯配置回调增加了可观察行为，不能只当语法替换。
