# Agent Note: Store 只面向项目写入者，清理与锁记录失败显式传播

Status: implemented

## Problem

Store 是项目专属仓库，写入者遵守同一协议。修复锁内已经完整重检对象，再为不遵守协议的写入者做第二次完整校验没有必要；上一轮把新增修复锁直接提升为 v2，也超出了用户确认的范围。

`DeletePart`、占用者登记及注销还会吞掉 I/O 或权限错误。登记失败却返回“已取得锁”会让错误伪装成成功；改成抛错后，文件句柄仍必须释放。

## Decision

- 保留获取修复锁后的第一次 Full 校验。隔离后的非覆盖发布若碰撞，按项目协议直接接受已校验的竞争者，不再做第二次 Full。发布和持锁发布的测试接缝收回为私有实现，不为不遵守项目协议的写入者增加防御分支。
- 当前没有发布版，所有仓库仍是 v1；恢复新建 v1 及既有 v1 可写，不迁移或降版实际仓库文件。只有用户明确提出相对前代写入不兼容需求后，才可提出版本／格式步进，并必须二次确认后实施。未来不支持的 writer 与锁禁用仍显式只读。
- 自有 `.part` 的清理错误显式传播。只有本次成功创建文件后才清理，不用 `File.Exists` 把访问错误变成不存在；设置属性时明确的 `FileNotFoundException` 表示发布已移走文件，正常结束清理。操作与清理同时失败时，局部 `AggregateException` 保留原操作和清理错误，不引入通用资源框架。
- `LockHolders.Register` 返回非空路径；登记、注销、旧记录清理或临时文件清理失败都显式传播。登记失败释放新打开的系统锁，注销失败仍在 `finally` 释放。
- 没有占用者目录或记录时，`Describe` 显示未知；列出的记录在打开前正常注销消失也可跳过，但捕获仅包住打开。枚举、解析、读取或旧记录删除的实际故障都显式传播。`FileLock` 在超时时保留主错误 `LockTimeout`，将真实记录读取错误与原锁冲突一起放进内部的 `AggregateException`，不新增诊断系统。

`Register` 返回非空记录路径。正常登记将临时文件原子移动为记录；登记失败时只清理本次创建的临时文件，清理失败与登记失败同时保留。`Unregister` 直接删除记录，不吞 I/O 或权限错误。`FileLock` 在登记失败后释放刚取得的句柄；注销即使抛错，也在 `finally` 释放句柄。这些释放只完成资源收尾，不继续业务。

本决定部分取代[修复锁](../../implemented/bug-fix/2026-10-27-store-repair-lock.md)的第二次校验及 v2 决定，以及[四处小缺陷](../../implemented/bug-fix/2026-10-27-store-small-fixes.md)和[下载与占用者记录](../../implemented/feature/2026-10-25-store-obtain-and-download-lock.md)中登记／清理降级的决定。修复锁的互斥、分片、锁序及 B04 根因保持不变。

## Alternatives considered

- **继续完整校验任何竞争者**：能识别不遵守项目协议的改动。不采用：这类写入者不在当前范围，正确竞争者已经先校验再发布，第二次哈希只增加 I/O。
- **为新增修复锁提升到 v2 并拒绝写入 v1**：能隔离不认识修复锁的旧程序。不采用：当前没有已发布前代；格式步进必须来自用户明确的兼容需求并二次确认，不能自行扩大本次修复。
- **清理或记录失败后继续成功**：少一次可见失败。不采用：用户要求暴露真实错误，资源释放应完成，但不能用成功结果掩盖登记或清理失败。

## Consequences

- 占用者记录目录故障会让本次锁获取失败，这是显式失败决定的代价。
- 操作与清理同时失败时调用方需要查看聚合的两份错误；不能只依赖旧的单一异常类型。
- 收益：只维护项目协议内的并发状态，不多读一次大文件；v1 仍可读写，格式演进不会由实现自行触发。清理和登记失败不再表现为成功，失败后系统锁仍释放。

### 验证

- 关键错误语义先红后绿：`dotnet test tests/Haytham.Core.Store.Tests --filter "FullyQualifiedName~Part_cleanup_failure_is_visible|FullyQualifiedName~Registration_failure_is_reported|FullyQualifiedName~Unregistration_failure_is_reported" --nologo`。原语义 4/4 失败：实际清理、登记、注销故障被吞掉；实现后 4/4 通过。
- `.part` 清理使用 Windows 真实的无删除共享句柄，分别验证单一清理错误和原操作加清理错误。新建与正常发布后的缺失生命周期由纳入测试覆盖。
- 登记目标被目录占用、旧记录 JSON 损坏、注销目标变成目录等实际失败路径验证错误可见；去除阻塞后能再次获取系统锁。超时读取记录被占用时，`LockTimeout` 保留原始读取错误。
- 原“占用者目录被删除仍超时”用例同时断言注销的 `DirectoryNotFoundException`，并确认系统锁已释放；测试收尾重建目录，不在生产代码中降级。
- 保留真实受控的双纳入及纳入／下载修复测试、取消与超时、跨进程锁及新建／现有 v1 可写测试。删除调用已收回私有阶段的 3 个测试，不保留为测试存在的发布入口。
- 最终检查范围为 Store 测试项目、受影响 C# 格式、子模块 `npm run verify-notes`；本次本机只运行 Windows，不把源码推理当 Linux／macOS 实测。
