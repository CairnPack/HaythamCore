# 需要时读：归档、笔记的清理与冻结

> 整理自 [DeepSeek Harness](https://github.com/deepseek-ai/deepseek-harness) 的笔记管理做法。收尾、复盘或大版本发布时对照；日常改动只需要顺手处理相关的那几篇。

**目录**：§0 什么时候做（日常 vs 集中整理）｜§1 怎么判断过时（1.1 一定保留 / 1.2 归档标准 / 1.3 直接清理 / 1.4 示例）｜§2 归档的操作（命令行）｜§3 归档后不能再改

---

## 0. 什么时候做：日常顺手 vs 集中整理

不用每次改代码都把所有笔记扫一遍，按情况处理：

1. **日常提交（绝大多数情况，不用扫全部笔记）**：
   - **原地更新**：改了哪个模块，就顺手更新负责这个决定的那篇笔记里的事实。
   - **当场审计**：新增笔记时，按模块名、关键词搜活跃笔记，当场归类（无关／部分重叠就互链／被完全吸收就删除或归档／过时的提案转 rejected 或删除）。已经知道相关的，不要推迟到集中整理。
2. **集中整理（少数情况，需要时才做）**：
   - 只处理日常没搜到的遗漏：季度复盘、大版本发布，或者活跃笔记多到影响查找时，集中扫一次。

## 1. 怎么判断过时

判断过时**不看篇幅，也不看写了多久**，只看一点：以后的人改代码时，它还能不能防止出错。

### 1.1 一定保留在 `implemented/` 的（年代再久也不归档）

有下面任何一种内容，就不算过时，不能归档：

- **职责边界**：规定了模块之间谁能调用谁、各负责什么（例如“界面层不能直接连数据库”）。
- **“绝不做某事”的承诺**：明确承诺不提供某项能力，或永远不兼容某个旧协议。
- **安全与合规的底线**：防止注入、绕过认证、数据泄露的硬性约束。
- **容易被再提出的被否方案**：Alternatives considered 里记录了看起来很好、但实际证明会导致死锁或崩溃的做法。

### 1.2 归档的标准（移到 `archived/`）

只对 `implemented/` 里符合下列条件的笔记归档：

- **被新架构完全取代，但还有单独的参考价值**：新笔记已经接手核心内容，旧篇里还留着“绝不做某事”的承诺、职责边界或重新引入的条件——归档，互链写在新笔记里。能删就删，见 `references/when-to-write.md` §4。
- **一次性的设计与很窄的细节**：一次性的界面间距调整、已经不支持的平台上的单点适配、已经修好的简单缺陷。

### 1.3 直接清理、不进归档的

- **`proposed/` 不归档**：前提已经不存在（例如依赖升级后自带了这个能力），或者不再推进的提案，直接改成 `Status: rejected — <一句话原因>`；已经被其他方案吸收的直接关闭。
- **没有价值的 `rejected/` 直接删除**：被否方案依赖的旧技术或 API 已经彻底移除，以后不可能再有人提出同样的做法，就直接删掉文件。

### 1.4 判断示例

来自 DeepSeek Harness 的归档 skill。判断时参考的是**理由**，不是字数；字数只是为了说明篇幅不是标准。

**应该归档的 implemented（决定已经完成，理由不太可能再影响以后的工作）：**

- 折叠侧边栏的控制栏（约 530 词）：已经完成的次要界面行为；
- 某个 CLI 参数的适配（约 1,500 词）：实现细节很多，但对以后的设计几乎没有影响；
- 文档生成流程（约 920 词）：工具已经完成任务，现在的生成器本身就说明了一切。

**应该保留的 implemented（理由仍然约束着现在的代码）：**

- 事件溯源的会话存储（约 250 词）：基础的持久化边界；
- 跨产品的职责划分规则（约 600 词）：一条职责边界；
- 项目会话目录的规则（约 630 词）：长期存储与身份的规则；
- 并行的 pre-push 检查（约 400 词）：边界情况，但仍然决定检查怎么排；
- 已下线的图片内容块（约 330 词）：保留到支持多模态为止，因为里面写着重新引入的条件。

**rejected 留还是删：**

- 保留“合并压缩包拆分”（约 430 词）：仍然有人会想合并，记录能防止重犯；
- 删除“经工具调用推送流式进度”（约 970 词）：依赖的 ACP／界面前提已经不存在；
- 删除“去掉 ACP 终端元数据”（约 360 词）：后来的自动化决定已经回答了这个问题。

## 2. 归档的操作

建议直接用命令行（移动文件、写入 manifest、列出失效的入站链接一次完成，**不依赖 git**）：

```bash
npx tsx .agents/skills/write-notes-like-deepseek/scripts/archive-agent-note.ts \
  .agents/notes/implemented/<class>/<filename>.md \
  [--superseded-by .agents/notes/implemented/<class>/<新笔记>.md]
```

命令依次做这些事：

1. **加归档标记**：在 `Status: implemented` 的**下一行**插入 `Archived: YYYY-MM-DD`（第 3、4 行之间不能有空行——这是和 DSH 原版一致的格式，校验脚本逐行检查）：
   ```markdown
   # Agent Note: xxx

   Status: implemented
   Archived: 2026-08-31

   ## Problem
   ...
   ```
2. **移动文件**：`implemented/<class>/...` → `archived/<class>/...`（用 git 时建议用 `git mv` 保留历史；命令本身直接移动文件，没有 git 也能用）。
3. **写入 `archived/manifest.json`**：记录这个文件的 SHA-256。之后归档内容只要被改过，`verify-archived` 就会报错。
4. **列出失效的入站链接**：扫描活跃笔记里指向这篇的相对链接（按链接解析，不是文本匹配），列出需要人工修正的地方。
5. **可选的 `--superseded-by`**：检查新笔记是否存在，并在**新笔记**末尾加一条指向归档路径的相对链接。不改归档的那篇。

除了开头的 `Archived:` 一行，**归档正文的任何字符都不能改**。

> 补录旧数据：如果 `archived/` 里已经有笔记、但还没有 manifest（例如从 DSH 导入的笔记），运行一次
> `npx tsx .agents/skills/write-notes-like-deepseek/scripts/verify-archived-agent-notes.ts --write`。它会先确认已有的记录没有被改过，再补上缺少的记录，不会改写已有的记录。

## 3. 归档后不能再改

一旦进入 `archived/`：

- **只读**：不能编辑、翻译、重新排版、更新、移动或删除。
- **由脚本检查**：`verify-archived` 检查开头格式、manifest 哈希，以及 manifest 只增不改（有 git 时与基线 ref 比较，可用 `AGENT_NOTE_ARCHIVE_BASE_REF` 指定基线，默认 HEAD；没有 git 时自动降级为只核对哈希，并给出提示）。已有的记录被改动或删除就报错。
- **日常检查跳过它**：`verify-agent-note-tree` 和 `verify-agent-note-format` 默认跳过 `archived/`，归档笔记里的链接失效不会让日常检查失败。
- **不能作为现在行为的依据**：代码有冲突或做架构评审时，以 `implemented/` 为准，`archived/` 只用来查历史；谁取代了谁，以新笔记里的互链和改过的入站链接为准。

上面的命令都从宿主项目根目录执行；skill 装在其他位置时，把 `.agents/skills/write-notes-like-deepseek` 换成实际路径。
