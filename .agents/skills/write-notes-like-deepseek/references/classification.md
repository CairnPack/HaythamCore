# 需要时读：分类（class）

> SKILL §1 的细则。新建笔记、选分类时对照。

## 固定的 6 个分类（要加新的得改检查脚本）

| 分类 | 范围 |
|---|---|
| `feature` | 新增用户或模型看得到的能力 |
| `bug-fix` | 修缺陷，或补上复盘发现的漏洞 |
| `simplification` | 不增加能力，只删代码、行为或对外暴露的部分 |
| `architecture` | 发布出去的源码的结构：包之间怎么依赖、运行时用哪些概念 |
| `process` | 代码以外的工具、规则与流程：检查、包管理、引入第三方代码等 |
| `testing` | 测试基础设施与测试策略 |

判断方法：

- `architecture` 与 `process`：前者是“发布出去的源码长什么样”，后者是“围绕源码的工具和工作流程”。
- 不单列 `refactor`：用 `simplification` 的标准判断——看得到的行为变了没有。没变就是 simplification；变了就归到 feature、bug-fix 或 architecture。
- `feature` 不只用于“新增能力”：**用户或下游看得到、又不明显的行为或产品选择，够不上架构的，也归 `feature`**。判断标准是“行为能不能被用户或下游观察到”，不是“改了多少代码”。只有局部的实现细节、普通的重构、不改变行为的依赖补丁才不写笔记。
- 拿不准时，想想以后谁会来找这篇笔记：找能力怎么演变的看 `feature`，找结构决定的看 `architecture`，找检查与发布规则的看 `process`。

每篇笔记都要满足、但脚本检查不了的要求：

- **备选方案只记真正考虑过的**：先写它最有力的理由，再写为什么不采用。只写缺点就否掉，等于没有认真比较。“不做／维持现状”只有当时真的考虑过才写，不要编。
- **简化要写清上限**：`simplification` 的 `## Consequences` 要写明这个取舍的已知上限是什么、出现什么情况时要重新考虑。没写重新考虑条件的简化，会在不知不觉中变成永久的。
- **验证要能核对**：写“改对了”时，要落到别人能检查的地方（哪条路径、多大的量、运行什么命令确认）。没有对比基线时，不要写“提升了”“更快了”这类相对的说法；这种没有验证过的说法比不写更糟。

## 检查脚本

`scripts/agent-note-tree.ts` 用常量 `AGENT_NOTE_CLASSES` 定义分类；遇到未知的分类目录，或直接放在 lifecycle 目录下的 `.md` 文件，都会报错。要加分类，必须同时改这个常量和本文，否则检查会失败。

分类与判断标准沿用 [DeepSeek Harness](https://github.com/deepseek-ai/deepseek-harness) 的笔记分类做法。
