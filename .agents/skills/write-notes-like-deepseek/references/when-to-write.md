# 需要时读：什么时候写、什么时候改，以及笔记状态的变化

> SKILL §4 的细则。每次做重要改动或评审时对照一次。

## 基本做法：更新负责这件事的那篇笔记，不要重复新建

DSH（deepseek-ai/deepseek-harness）的 git 历史里，新增的笔记很少，绝大多数改动是**原地修正已有笔记里的事实**。
笔记不是写完就放着的文章，也不是修改日志；它描述的是代码现在的样子，要随代码一起改。

一篇笔记不能被改成另一个决定：事实（路径、符号、默认值）原地改；决定或理由变了，新开一篇，两篇互相链接。不要把 `## Decision` 改成相反的结论，也不要让 git 历史成为旧理由的唯一副本。

---

## 1. 各种情况怎么处理

| 情况 | 做什么 | 说明 |
|---|---|---|
| **重构、改名、移动包、改默认参数** | **原地更新已有笔记里的事实** | `Decision` 的核心理由不变，直接改路径、类名、默认值，不追加修改记录。理由变了就新开一篇，不原地改 |
| **写新笔记之前** | **当场审计活跃笔记** | 按模块名、关键词搜 proposed、implemented、rejected；每篇命中的当场归类（无关／部分重叠／被完全吸收／过时的提案），和新笔记一起提交。不要留到以后集中整理 |
| **提出新的架构尝试或技术选型** | **在 `proposed/` 新建** | 写代码之前，写清动机、真正考虑过的备选方案与验收标准 |
| **开发完成、准备合进主干** | **改成 `implemented/`** | 按 §3 的清单改写；和代码一起提交（用 git 时就是同一个 commit 或 PR） |
| **方案被新决定部分取代** | **两篇都保留、互相链接** | 只更新仍然成立的事实。不要归档 |
| **方案在评审中被否决** | **移到 `rejected/` 或删除** | 只有它的理由能防止以后重犯时才保留，并写清原因；否则直接删除 |
| **新架构完全取代了旧架构** | **先把内容并入新篇，能删就删，否则归档** | 见 §4。指向关系写在新笔记里，不写进归档的那篇 |
| **发布打 tag、依赖小补丁、排版** | **不用写** | 直接提交，不需要笔记 |

## 2. 原地更新的规则

负责某个模块的笔记，在模块有变化、但核心决定没有被推翻时：

1. **直接改，不追加修改记录**：
   - ❌ 不要在文末追加 `### 2026-09-02 更新：类名改为 X`
   - ✅ 直接把正文里的旧类名换成新类名，保证任何时候打开这篇笔记，看到的都是当前主干的事实。
2. **一直用现在时**：
   - 写“系统使用 SQLite 存储”，不要写“系统不再使用 JSONL，现在改用 SQLite”。脚本只拒绝提案式的标题，不检查时态，现在时要靠写的人自己守。

---

## 3. proposed → implemented 的改写清单

在同一次改动里做完：

1. 移到 `implemented/<class>/`，文件名日期不变（第一次提出的日期）
2. `Status: proposed` → `Status: implemented`
3. `## Proposal` → `## Decision`，改成现在时（已经实现的事实）
4. `## Acceptance criteria`／`## Risks` 并入 `## Consequences`（或现在时的 `## Testing`／`## Verification`）
5. 删掉计划性的段落（`## Plan`、迁移步骤、开放问题）

脚本按结构检查：implemented 里还留着 `## Proposal` 就会失败。

---

## 4. 部分取代与完全取代

**部分取代**：新方案只覆盖旧方案的一部分 → 两篇都保留，互相加相对链接；只更新仍然成立的事实。不要归档，也不要推迟处理。

**完全取代**（旧方案彻底不用了）：

1. **整理旧笔记里有用的内容**：它独有的安全边界、“绝不做某事”的承诺、失败场景、在什么条件下可以重新引入、还没验证的地方。
2. **并入新笔记**：写进新篇的 `## Decision`／`## Alternatives considered`／`## Consequences`。
3. **旧笔记二选一**：
   - **删除**：新篇已经包含旧篇全部独有的内容，指向旧篇的链接也都改好了 → 直接删除，不放进 `archived/`。
   - **归档**：旧篇还有单独的参考价值（“绝不做某事”的承诺、职责边界、重新引入的条件）→ 用 `archive-agent-note.ts` 归档。只加一行 `Archived:`；互链写在新笔记里。
4. **修正指向旧篇的链接**：把仍然指向旧路径的相对链接改成指向新笔记（只有引用历史版本时才指向 `archived/`）。

`--superseded-by` 只检查新笔记是否存在，并在新笔记末尾加一条指向归档路径的相对链接。

## 5. 可选：在源码入口加注释

宿主项目如果有这个习惯，可以在核心入口加一行：

```typescript
// Note: 会话持久化采用文件句柄管理，避免并发写冲突 — 见 .agents/notes/implemented/architecture/2026-08-27-handle-based-session-persistence.md
export class SessionFileHandlePool {
  // ...
}
```

这不是必需的。`check-note-anchors` 只报告、不拦截，不放进 CI。
