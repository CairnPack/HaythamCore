# 需要时读：写完笔记后的意思自查

> 结构交给脚本检查，这张清单检查意思。写完后自查，只向用户报告缺口和写得好的地方，不要逐条复述。
> 这是写笔记的人自己做的检查，不是脚本规则——下面每一项都要靠判断，不会放进 verify 脚本。

## 动手之前：先自己查，再问用户

- [ ] 这个问题真的需要用户决定吗？用 SKILL §3 的四种方法（入口注释、按目录查、rg、模块文档）能查到的事实，自己查，不要问用户。只有取舍和拍板才占用用户的时间。

## Problem

- [ ] 动机不依赖方案也成立：把 Decision 删掉再读一遍，问题还是同一个吗？
- [ ] 起因写清楚了：什么出了问题、什么要改、不改会怎样。

## Decision／Proposal

- [ ] 具体到可以照着做：不是“用更好的数据库”，而是“会话存储用 SQLite”。
- [ ] 理由来自比较：写了“决定用 X”，就补一句“X 和 Y 相比为什么选 X”。

## Alternatives considered

- [ ] 有真正考虑过的备选方案（通常至少两个），不要编；确实没有时正文写“无”。“不做／维持现状”只有当时真的考虑过才算一个，不是必须有。
- [ ] 每个被否的方案先写它最有力的理由，再写为什么不采用；只写缺点就否掉，等于没有认真比较。
- [ ] 不采用的理由要落到具体的条件，不能只说“经验上不行”。

## Consequences

- [ ] 代价和收益都写。问自己：什么变难了？维护成本是什么？只写收益的后果是挑过的。
- [ ] 简化要写清已知的上限，以及什么时候要重新考虑。没写重新考虑条件的简化，会在不知不觉中变成永久的。
- [ ] 没有对比基线就不用相对的说法：说不清基线时，“提升了”“更快了”改成直接陈述事实。

## Verification／Testing（implemented）

- [ ] 落到别人能核对的地方：哪条路径、多大的量、运行什么命令。
- [ ] 不写“看起来能用”：验收标准要么能逐项打勾，要么明确写明留给以后。

## 报告格式

自查完按下面的格式报告（一个缺口一行，没有缺口就不写这部分）：

```markdown
**意思自查：<filename>**
✅ 已经写好：动机能独立成立 / 有 2 个真正考虑过的备选方案 / 后果写了代价和收益
⚠️ 缺口：
- Alternatives —— 只比较了“做 vs 不做”，补一个与现在方案同级的真实备选
- Consequences —— “性能提升”要写明是哪条路径、多大的量
建议：改完以上 2 处再提交 / 缺口可以接受，直接提交
```

用户接受缺口就直接提交；不接受就改完再提交。这是判断，不是脚本，不要把它做成另一道检查。

## 怎么知道这份自查有用

隔一段时间回头看，出现下面的情况说明自查在起作用；这些情况消失了，说明它只是走过场：

- 问用户的问题里，**不再有**翻一下笔记目录或 rg 一下就能回答的事实问题。
- 报告里的每个缺口都附有**具体改法**（改哪一节、补什么），而不是“建议再完善”。
- `rejected/` 和 Alternatives 里被否掉的做法，**不再被新的会话重新提出**——这正是这套笔记存在的理由。
