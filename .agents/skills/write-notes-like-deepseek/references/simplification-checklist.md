# 需要时读：简化机会自查

> 整理自 [DeepSeek Harness](https://github.com/deepseek-ai/deepseek-harness) 的 `dsh-find-simplifications` skill。收尾或重构时看一遍；不要在功能改动里顺带塞进无关的简化。

## 可以删除、合并或降级的迹象

- 公开的方法、事件、配置项、包、持久化事件或测试产物，在生产代码里没有使用者（只有测试或文档用到，而且不是关键行为）。
- 同一个事实在两个地方表示（尤其是持久化事件与临时事件各存一份）。
- 某个接口要求所有实现都提供某个方法，但没有任何调用方用到它。
- 只为测试、demo 或辅助工具而存在的包，却增加了发布与依赖的成本。
- 为“以后可能要”而做的通用化：多会话、后台任务台账、半路改方向、工具自带界面等，现在没有归属。
- 为不存在的 API 准备的不变式、回滚、快照或特殊处理。
- 自己手写了成熟的现成包或当前 Node 版本已经提供的功能；换掉之后能真正删掉实现和对应的测试。

## 怎么确认

- 用 `rg` 搜符号、事件、配置键、包名，看生产代码（`packages/*/src`、`examples` 的运行时、`loader/config` 路径）是否真的在用。
- 分清生产代码、非生产代码和不确定的部分——测试与文档里出现不算生产代码在用；`knip` 可以辅助，但不能代替亲自看调用的地方。
- 小而确定的清理用 `TODO`／`FIXME`／`XXX` 记下，不要为此写笔记；只有长期有效的取舍才值得写一篇 proposed 笔记。
- 手写还是用依赖：看能净删掉多少（实现、测试、文档）、依赖的健康状况、是否贴合需求；能真正删掉代码才换，外面再包一层、复杂度不变的不算更好。

## 和笔记的关系

- 符合上面的迹象、而且这个取舍需要记下来 → 写 `proposed/simplification` 笔记（Problem／Proposal／Alternatives／Acceptance／Risks）。
- 已经完成的简化 → `implemented/simplification`，Consequences 同时写删掉的东西带来的代价和省下的维护负担。
- 笔记太多时，用 `archiving.md` 的“以后还有没有参考价值”判断是否归档，不看字数和时间。
